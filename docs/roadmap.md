# Roadmap

`[x]` is done, `[ ]` is not. Each step targets the upstream versions in
[compatibility](compatibility.md), and every item is built the same way: record real HA first,
build against the recording, add it to the CI replay
([testing](architecture.md#testing-differential-against-real-ha)). Design is in
[architecture.md](architecture.md); known shortcuts are under [Gaps](#gaps).

## The reference house

What "usable" means, concretely: the maintainer's own Home Assistant, a Raspberry Pi 4 running HA
Container 2026.11.2 (config and notes in the homelab repo, `devices/pi4`). lean-home is done for it
when it runs a copy of that config dir unchanged. Today it would log in with the house's users
and show almost nothing: the house has no MQTT devices, and everything below is still to do. Each
item names the roadmap step that covers it.

- [ ] **Dashboard** "Home": a storage dashboard (`.storage/lovelace.home_dash`, generated by
  `dashboard.py`) with tiles, history graphs and custom cards served from `/local` (`www/`:
  `talk-button.js`, the patched Xiaomi vacuum map card) and by integrations
  (`/webrtc/webrtc-camera.js`). Step 3.
- [ ] **Helpers**: 3 `input_select` and 1 `input_number` in YAML, 6 light groups (`group` config
  entries, made in the UI). Step 3.
- [ ] **YAML entities**: 7 `template` sensors and a trigger-based template, 8 `command_line`
  sensors (Pi CPU, temperature, fan, memory, disk, containers), 5 `rest` resources with 16
  sensors and a binary sensor (router over RouterOS REST, the printer's Moonraker), a
  `rest_command`. Step 3.
- [x] **Its automation** (`thermostat_room_sensor`): state and `time_pattern` triggers, queued mode
  with `max`, `variables`, and templates with `has_value`, `states[x].last_reported`, `now()` and
  `timedelta`. Step 2 (`time_pattern` and template helpers done).
- [ ] **History**: the dashboard's graphs, 7 days of history, a 30 s commit interval (flash wear).
  Step 4.
- [ ] **Companion app** (iOS, `mobile_app`), through the reverse proxy. Step 5.
- [ ] **Reverse proxy**: HTTPS only, through Caddy; HA trusts it with `use_x_forwarded_for` and
  `trusted_proxies` in `.storage/http`. Step 3.
- [ ] **Matter**: the thermostat (Honeywell X2S), through the `matterjs-server` container's
  WebSocket API. Step 8.
- [ ] **Cameras**: a Tapo C220 through the go2rtc container (`go2rtc`, a `generic` camera on its
  restream), PTZ and motion through `onvif`, talk-back through the WebRTC Camera custom
  integration. Steps 8 (go2rtc) and 7 (`onvif`, the custom one).
- [ ] **Python integrations**: `roborock` (+ the `roborock_custom_map` custom component), `tuya`,
  `alexa_devices`, `synology_dsm` (also the backup target), `adguard`, `met`, `ha_creality_ws`
  (custom), `radio_browser`, `google_translate`, `shopping_list`. Step 7.
- [ ] **Built-ins** from `default_config` the house uses: `sun`, `person`/`zone`, `backup`,
  `bluetooth` (the Pi's adapter). Steps 3 (`sun`, `person`, `zone`), 7 and 8 (the rest).

### Running it

Not a numbered step: what it takes to run lean-home somewhere real.

- [x] Docker image (`Dockerfile`): static musl build in `FROM scratch`, the pinned frontend without
  source maps or the ES5 build, zoneinfo. Built and smoke-tested in CI, not published.
- [x] Try it locally (`try/`): Mosquitto, simulated MQTT devices and lean-home in Docker Compose,
  with a setup script that onboards a fresh config dir with stock HA.
- [ ] Trim the frontend further (the image is 186 MB of content, 177 MB of it frontend; estimate
  20–30 MB):

  | Part | Size | Keep? |
  |---|---|---|
  | `frontend_latest` | 77 MB | One compressed copy of each file instead of three (source maps already dropped) |
  | `frontend_es5` (old browsers) | 84 MB | Dropped; make it opt-in if old wall tablets or Android WebViews need it |
  | `static/translations` | 87 MB | Brotli copies only: 9.4 MB for all languages, 0.25 MB for English |
  | `static/locale-data` | 24 MB | Likely cut down per language too |

  Check before dropping gzip: Chromium is believed to accept brotli only over HTTPS, and most
  people open the hub over plain HTTP on the LAN, so the gzip copies (~8 MB) may have to stay.
  Test it rather than guess.
- [x] aarch64 image (multi-arch build) for the Pi and the router.
- [x] Releases (release-plz: merging its release PR tags the version and creates the GitHub release)
  and the image published on each release (`.github/workflows/publish.yaml`):
  `ghcr.io/emerconn/lean-home:<version>` and `:latest`, amd64 and arm64.
- [ ] Measure on the target (1 GB ARM64): memory, idle CPU, startup time and image size, under the
  [measurement rules](architecture.md#measurement-rules). Until now everything was measured on the
  dev PC.
- [ ] Onboarding of its own, so a config dir doesn't have to come from HA first (with step 6).

## Gaps

Shortcuts we chose not to close yet. Each has a `shortcut:` comment at the code it affects; a
closed one is removed from this list (git history keeps it). *When* says when to do it, *why*
why it can wait.

### Templates

- [ ] **HA helpers not built yet**, by the HA test cases that need them (`ha_template_cases`
  prints the full list): datetime (`strptime` 26,
  `relative_time`/`time_since`/`time_until` 30, `today_at`, `as_local`, `timestamp_*`), math
  (`average`, `median`, `statistical_mode`, `log`, trig, bitwise, `clamp`, `min`/`max` as
  globals), state (`expand` 12, `closest`/`distance` 23, `state_translated`/`state_attr_translated`
  16, `integration_entities`), regex (24), collections (`flatten`, `combine`,
  `union`/`intersect`/`difference`…), areas/devices/floors/labels (~70), strings (`slugify`,
  `ordinal`, `wrap`), `typeof`, hashes, base64, `version`, issues. *When:* by what automations
  use; regenerate the count with the corpus.
  *Why:* each is small, with HA's cases waiting in the corpus: add it to `IMPLEMENTED` in
  `template_ha_cases.rs` and they start being compared.
- [ ] **Undefined-variable warnings** name the first undefined variable only, and none for a
  missing attribute of a defined variable or an `if`/`for` over an undefined (HA warns there too).
  *When:* the template editor shows a wrong warning. *Why:* errors and results are right; only
  the `report_errors` log text can differ.
- [ ] **No re-render rate limits**: HA waits up to 60 s before re-rendering a failed template, and
  limits `render_template` to 1/s for domain listeners and 1/min for all states. *When:* a
  dashboard iterating all states proves costly. *Why:* re-rendering on every change is correct,
  only more work.

### Automations and scripts

- [ ] **Script actions not built yet**: `wait_template`, `wait_for_trigger`, `repeat`, `parallel`,
  `sequence`, `event`, `scene`, device actions, service responses (`response_variable`). A script
  using one is unavailable, with the error in the log. *When:* step 2's actions item.
- [ ] **Conditions not built yet**: `sun`, `zone`, `device`. *When:* `sun` with step 2; the rest
  by demand.
- [ ] **Triggers not built yet**: `event`, `sun`, `device`…; time triggers at an `input_datetime`
  or timestamp sensor or with an offset; MQTT topic templates; `trigger_variables`; HA's
  `not_triggered` traces. An automation using one is unavailable, with the error in the log.
  *When:* step 2's trigger items. *Why:* each is small next to the engine; they share `fire()` in
  `automation.rs`.
- [ ] **Blueprints**: `!input` loads as a `{"!input": name}` marker, and `use_blueprint`
  automations aren't expanded. *When:* step 2's blueprints item.
- [ ] **Automation details**: an automation without an `id` stores traces under its object id (HA
  keeps none); no `automation_triggered` event or logbook entries. *When:* with the logbook.
- [ ] **Automation runs**: services act on one automation after another (HA calls them
  concurrently, which only matters when one `automation.trigger` names several); `trigger.for` is
  a `{"__type", "total_seconds"}` dict in templates, a timedelta in HA; time triggers at a time a
  DST change skips or repeats aren't checked against HA (lean-home fires once: at the first of two
  occurrences, and a skipped 02:30 at 03:30). *When:* concurrency when a config needs it,
  `trigger.for` with the datetime helpers, DST with a recording across a change.
- [ ] **Script details**: traces aren't kept across restarts (HA's `.storage/trace.saved_traces`);
  field defaults and non-entity selector defaults in `get_services`; branch-local variables (HA
  lets a branch update an outer variable); `continue_on_error` skips every error (HA stops on
  configuration errors). *When:* saved traces when the trace pages need history across restarts;
  the rest when a config needs it.
- [ ] **Script variables**: `variables:` are rendered in order, each seeing the ones before it,
  and the caller's run variables are applied after them (HA lets run variables win and renders
  with them in scope). *When:* a config relies on a default that reads a run variable.

### Editors

- [ ] **Saving**: only the required keys are validated (HA checks the whole schema and answers
  400; lean-home saves, and the entity is unavailable with the error in the log); the save answers
  after the reload (HA answers first); a removed automation's MQTT topic stays subscribed; keys
  over 128 characters (libyaml's `? key` form) and integers past 2^64 aren't written as HA writes
  them. *When:* full validation once lean-home knows the whole schema; the rest when a config
  needs it.
- [ ] **Details**: blueprints, categories and `frontend/get_icons` answer empty (the frontend uses
  its built-in icons); config entries claim no options, reconfigure or unload support, and
  `type_filter` is ignored; `subscribe_condition` re-checks on every state change, doesn't poll
  `for:` each second and doesn't forward `template_errors`. *When:* icons with translations,
  blueprints with step 2, the rest when the integrations page or a config needs it.

### Config, YAML and storage

- [ ] **Packages**: only `automation` and `script` are merged (the domains lean-home reads); a
  package's other domains are left out, with no error where HA would log one; error messages don't
  name file and line. *When:* each domain with the integration that reads it.
- [ ] **YAML corner cases**: non-string keys become Python's `str()` of them (`1:` → `"1"`),
  `.inf`/`.nan` become strings, dates become strings; so an editor save writes such a value back
  quoted (`'2026-11-25'`, `'1': x`) where HA writes it as it was. *When:* a config needs them.
- [ ] **`homeassistant:` keys** beyond location and units (`customize`, `allowlist_external_dirs`,
  `media_dirs`, `auth_providers`…). *When:* with the features that use them.
- [ ] **Registries are read-only**: new MQTT entities, and automations and scripts created in the
  editor, aren't written to `core.entity_registry` (HA later picks the same ids, normally; a
  renamed alias would give HA and lean-home different ids). *When:* step 6.
- [ ] **Restore state**: only automations and scripts are lean-home's restore entities; HA's MQTT
  entities keep the entry HA last wrote until it expires (7 days), and nothing is restored for
  them (their state comes from retained messages). *When:* if lean-home restores MQTT entities
  (optimistic ones, `expire_after` sensors).

### HTTP and auth

- [ ] **No onboarding**: a config dir must come from HA first. *When:* step 6.
- [ ] **HA's opt-in IP ban** (`http: login_attempts_threshold`, `ip_bans.yaml`). *When:* a user
  asks. *Why:* off by default in HA too; lean-home already serializes password checks and backs
  off per IP.

### MQTT

- [ ] **Platforms beyond the four** (cover, climate, fan, button, number, select…). *When:* by
  what MQTT users' devices expose.
- [ ] **Template-schema lights** (`schema: template`). *When:* a device needs it.
- [ ] **Device discovery `child_devices`** (HA 2026.x). *When:* a firmware sends it.
- [ ] **WebSocket transport**. *When:* a user needs it (brokers behind a reverse proxy).
- [ ] **MQTT v5** (HA's default for new entries): not planned; 3.1.1 works with every broker HA
  supports.
